# 공개 섹션 활성화·비활성화 설계

## 목표

관리자가 사이트 설정에서 홈을 제외한 최상위 공개 섹션을 켜거나 끌 수 있게 한다. 비활성화는 사용자 역할과 무관하게 공개 화면에 적용하며, 헤더 메뉴만 숨기는 데 그치지 않고 직접 URL과 관련 공개 API도 차단한다. 편집자와 관리자는 비활성화된 섹션의 콘텐츠를 `/manage`에서 계속 준비할 수 있어야 한다.

이 기능은 보안 비밀을 저장하기 위한 접근 제어가 아니라 게시 제어다. 일반 방문 경로와 공개 API에서는 비활성 콘텐츠를 제공하지 않지만, 정적 export에 포함된 고정 문구를 배포 파일 수준에서 제거하지는 않는다.

## 결정

기존 전역 사이트 설정에 `sectionAvailability`를 추가한다. 홈은 항상 활성화하고 다음 일곱 섹션만 제어한다.

- `about` — 소개
- `worship` — 예배
- `mokjang` — 목장
- `events` — 이벤트
- `sermons` — 설교
- `resources` — 자료·신청
- `contact` — 문의

각 값은 역할별 규칙이 없는 단일 boolean이다. 공개 페이지에서는 익명 방문자, 회원, 편집자, 관리자 모두 같은 상태를 본다. 운영 메뉴와 `/manage` 경로는 이 설정의 영향을 받지 않는다.

메뉴 이름 변경, 순서 변경, 하위 페이지별 제어, 역할별 공개, 예약 공개는 포함하지 않는다.

## 현재 구조와 선택 이유

- 공개 메뉴는 `Header.tsx`에 고정 배열로 정의되어 있다.
- 테마, 사진, 교회 정보, 페이지 문구는 익명 GET과 관리자 PUT을 제공하는 `/api/site-settings`를 통해 전역으로 배포된다.
- `ThemeProvider`가 사이트 시작 시 전역 설정을 읽어 헤더, 푸터와 각 페이지에 제공한다.
- 앱은 Next.js 정적 export이므로 데이터베이스 값에 따라 SWA 경로 규칙이나 HTTP 상태를 실시간으로 바꿀 수 없다.

따라서 기존 설정 흐름을 확장하고 클라이언트 페이지 가드와 서버 공개 API 가드를 함께 두는 방식이 현재 아키텍처에서 가장 작은 완전한 변경이다. 메뉴만 숨기는 방식은 직접 URL과 API를 열어 두므로 요구사항을 충족하지 않는다. 서버 렌더링이나 프록시로 이전하는 방식은 정적 파일 자체까지 보호해야 할 때만 필요하며 이번 범위를 넘는다.

## 데이터 모델

`dbo.SiteSettings`에 `SectionAvailabilityJson NVARCHAR(MAX) NULL` 열을 idempotent schema migration으로 추가한다.

클라이언트와 서버의 정규화 결과는 다음 의미를 갖는다.

```ts
type PublicSection =
  | 'about'
  | 'worship'
  | 'mokjang'
  | 'events'
  | 'sermons'
  | 'resources'
  | 'contact';

type SectionAvailability = Record<PublicSection, boolean>;
```

- 기존 행처럼 열이 `NULL`이거나 저장된 객체에 키가 없으면 해당 키는 `true`다.
- 이는 배포 직후 기존 사이트가 예기치 않게 닫히지 않게 하는 마이그레이션 기본값이다.
- 관리자 PUT은 알려진 키의 boolean만 받아 정규화한다.
- PUT에서 `sectionAvailability`가 생략되면 기존 값을 보존해 이전 클라이언트가 설정을 초기화하지 않게 한다.
- 새 클라이언트는 저장할 때 정규화된 일곱 값을 모두 보낸다.
- 알 수 없는 키는 저장하지 않는다.

`/api/site-settings` GET 응답과 클라이언트 `SiteSettings` 및 `SiteSettingsPayload`에 정규화된 값을 포함한다. 저장 감사 필드인 `UpdatedBy`와 `UpdatedAt`은 기존 전역 설정과 함께 갱신한다.

## 섹션 레지스트리와 경로

클라이언트에는 공개 경로를 섹션으로 변환하는 하나의 레지스트리를 둔다.

- `/about` → `about`
- `/worship` → `worship`
- `/mokjang` 및 `/mokjang/*` → `mokjang`
- `/events` 및 `/events/*` → `events`
- `/sermons` → `sermons`
- `/resources` → `resources`
- `/contact` → `contact`

쿼리 문자열은 경로 판정에 영향을 주지 않는다. `/`, `/manage`, `/manage/*`, `/profile`, `/login`, `/settings`와 알 수 없는 경로는 이 가드가 차단하지 않는다.

같은 모듈이 다음 기능을 제공한다.

- 경로가 속한 공개 섹션 찾기
- 섹션의 활성 상태 확인
- `href`가 현재 노출 가능한지 확인
- 헤더에 표시할 일곱 메뉴의 메타데이터 제공

API 런타임은 앱 TypeScript를 직접 공유하지 않으므로 `api/shared`에 동일한 일곱 키를 사용하는 작은 서버 전용 모듈을 둔다. 양쪽의 키와 매핑은 각각 단위 테스트로 고정한다.

## 사이트 설정 화면

기존 설정 작업 공간에 네 번째 탭 `메뉴 공개`를 추가한다.

- 일곱 섹션을 현재 메뉴 순서로 표시한다.
- 각 항목은 활성/비활성 스위치와 영향 범위 설명을 갖는다.
- 설명은 공개 페이지와 관련 공개 조회만 닫히며 운영 화면의 작성·저장은 유지된다고 명시한다.
- 토글은 초안만 바꾸며 기존 `전체 적용 저장` 전에는 게시하지 않는다.
- 변경 탭 점, 저장 요약, 전체 편집 취소와 dirty-state 계산에 새 탭을 포함한다.
- 저장 성공 시 전역 context를 즉시 갱신해 관리자가 보는 현재 브라우저에도 바로 반영한다.

별도 확인 대화상자, 메뉴 재정렬, 사용자 정의 메뉴명은 추가하지 않는다. 기존 전역 저장과 취소 흐름이 게시 의도를 충분히 명시한다.

## 방문자 화면

### 링크 노출

활성 상태는 헤더뿐 아니라 사이트가 제공하는 모든 주요 내부 진입점에 적용한다.

- 헤더 최상위 메뉴
- 푸터 탐색 링크와 문의 CTA
- 홈의 빠른 링크, 주간 안내 링크와 본문 CTA
- 페이지 본문의 다른 제어 대상 섹션 링크

링크 대상의 pathname을 공통 helper로 판정한다. 비활성 링크는 클릭 불가 텍스트로 남기지 않고 렌더링하지 않는다.

### 직접 URL

`Layout` 내부의 중앙 페이지 가드가 현재 pathname을 검사한다.

- 사이트 설정을 처음 확인하는 동안 제어 대상 페이지의 원래 본문을 렌더링하지 않는다.
- 활성 섹션이면 기존 페이지를 그대로 렌더링한다.
- 비활성 섹션이면 원래 페이지 대신 이중 언어 `현재 비공개인 페이지입니다` 안내와 홈 이동 버튼을 렌더링한다.
- 헤더와 푸터는 유지하되 해당 섹션 링크는 숨긴다.
- 비활성 페이지에는 동적으로 `robots`의 `noindex, nofollow`를 적용한다.
- 역할은 페이지 판정에 사용하지 않으므로 관리자도 공개 URL에서는 같은 비공개 화면을 본다.

정적 export의 제약으로 비활성 페이지 요청의 HTTP 상태는 동적으로 404가 되지 않고 200인 채 안내 화면을 보여준다. 검색엔진 캐시와 정적 배포 파일에서 고정 문구를 즉시 제거하는 기능도 제공하지 않는다.

### 반영 시점

- 저장을 실행한 관리자 브라우저는 context 갱신으로 즉시 바뀐다.
- 새로 앱을 연 방문자는 최초 설정 조회에서 최신 상태를 받는다.
- 이미 열려 있는 다른 브라우저 탭의 정적 본문을 실시간으로 강제 제거하지 않는다. 새로고침 전까지 이전 정적 문구가 남을 수 있다.
- 공개 API 차단은 설정 저장 이후의 새 요청부터 즉시 적용한다.

실시간 polling, WebSocket 알림과 강제 로그아웃은 범위에서 제외한다.

## 서버 API 차단

`api/shared`에 현재 `SectionAvailabilityJson`을 읽고 섹션 상태를 판정하는 공통 가드를 둔다. 관련 공개 동작은 데이터를 읽거나 SAS URL을 만들기 전에 이 가드를 호출한다.

비활성 상태에서 차단할 공개 동작은 다음과 같다.

- `mokjang` — 목장 GET
- `events` — 이벤트 GET
- `sermons` — 설교 GET
- `resources` — 자료 GET, 신청 GET
- `contact` — 문의 POST
- 파일 다운로드 — 자료, 설교, 이벤트, 목장 파일의 새 SAS 발급

소개와 예배는 별도 공개 API가 없어 클라이언트 페이지 가드만 적용한다.

### 운영 예외

목장, 이벤트, 설교, 자료와 신청의 관리 화면은 기존 GET을 이용한다. 따라서 섹션이 비활성일 때도 `editor` 또는 `admin` 역할의 관리용 조회는 허용한다. 기존 관리 POST, PUT, DELETE와 업로드도 그대로 허용한다.

이 예외는 `/manage`에서 콘텐츠를 준비하기 위한 것이다. 공개 페이지 가드는 역할과 무관하게 적용하므로 편집자와 관리자도 공개 URL의 원래 화면을 볼 수 없다.

문의 POST에는 관리 준비 용도가 없으므로 역할 예외를 두지 않는다.

### 응답

비활성 섹션을 익명 방문자나 일반 회원이 조회하면 다음 의미의 404 응답을 반환한다.

- HTTP 404
- 안정적인 오류 코드 `SECTION_UNAVAILABLE`
- 짧은 한글·영문 메시지
- `Cache-Control: no-store`

404를 사용해 비활성 데이터의 존재 여부를 불필요하게 드러내지 않는다. 클라이언트 페이지 가드가 정상 동작하면 공개 화면은 이 오류를 직접 표시하지 않는다.

### 다운로드

현재 다운로드 조회 SQL은 파일 종류를 함께 반환하도록 확장한다.

- `Resources` → `resources`
- `SermonFiles` → `sermons`
- `EventImages` → `events`
- `MokjangImages` → `mokjang`

파일의 기존 visibility와 역할 검사 전에 섹션 상태를 확인하되, 편집자와 관리자의 관리용 다운로드는 허용한다.

새 SAS 발급은 비활성화 직후 차단된다. 이미 발급된 짧은 수명의 SAS URL은 만료 전까지 회수할 수 없으며, Storage 키 교체처럼 전체 URL을 무효화하는 조치는 수행하지 않는다.

## 실패 처리

게시 제어의 목적을 우선해 런타임 조회 실패는 `fail closed`로 처리한다.

- 클라이언트가 `/api/site-settings`를 읽지 못하면 홈과 운영 영역은 유지하지만 일곱 제어 대상 공개 페이지의 본문과 링크는 닫는다.
- 서버가 공개 API 요청 중 설정 상태를 확인하지 못하면 데이터를 반환하지 않고 5xx를 응답한다.
- 정상적인 마이그레이션 상태인 `NULL`, 빈 설정 객체 또는 누락 키는 실패가 아니며 모두 활성으로 정규화한다.
- malformed JSON은 로그에 남기고 제어 대상 공개 API를 닫는다.
- 설정 PUT 검증 실패는 기존 설정을 바꾸지 않고 400을 반환한다.

권한 검사는 그대로 유지한다. 섹션 활성화가 기존 회원·편집자·관리자 권한을 확대하지 않으며, 섹션 비활성화도 운영 쓰기 권한을 새로 부여하지 않는다.

## 테스트

### 클라이언트

- `NULL` 또는 누락 키가 모두 활성으로 정규화된다.
- 명시적 `false`와 잘못된 값이 정의된 규칙대로 처리된다.
- 각 공개 pathname과 상세 pathname이 올바른 섹션으로 매핑된다.
- 쿼리 문자열이 매핑을 바꾸지 않는다.
- `/manage`와 다른 비대상 경로는 차단되지 않는다.
- 비활성 링크가 헤더, 푸터와 홈 진입점에서 사라진다.
- 최초 설정 확인 전 원래 페이지 본문이 노출되지 않는다.
- 비활성 직접 URL이 공통 안내 화면과 `noindex`를 표시한다.
- 설정 dirty-state, 전체 취소와 저장 payload에 새 탭이 포함된다.

### API

- 기존 DB 행의 `NULL`은 모두 활성으로 응답한다.
- GET과 PUT이 일곱 boolean을 round-trip하고 알 수 없는 값을 저장하지 않는다.
- PUT에서 필드가 생략되면 이전 설정을 보존한다.
- 비활성 공개 GET은 익명·회원에게 404를 반환하고 데이터를 읽지 않는다.
- 같은 GET은 편집자·관리자에게 운영 목적으로 허용된다.
- 비활성 문의 POST는 역할과 무관하게 차단된다.
- 파일 종류가 올바른 섹션으로 매핑되고 새 SAS 발급이 차단된다.
- 기존 쓰기 권한 검사가 그대로 동작한다.
- 설정 조회 오류가 공개 데이터를 노출하지 않는다.

### 통합 확인

- 타입 검사와 모든 단위 테스트를 실행한다.
- Next.js production 정적 build가 성공하는지 확인한다.
- 홈은 모든 조합에서 접근 가능하고 `/manage`는 기존 역할 규칙만 따르는지 확인한다.
- 일곱 섹션을 각각 끄고 헤더, 푸터, 홈 링크, 직접 URL과 관련 API를 수동 점검한다.

## 완료 기준

- 관리자는 사이트 설정 한 곳에서 일곱 최상위 공개 섹션을 독립적으로 켜고 끌 수 있다.
- 홈과 운영 메뉴는 끌 수 없다.
- 비활성 섹션은 역할과 무관하게 공개 메뉴, 내부 진입 링크와 직접 URL에서 원래 화면을 제공하지 않는다.
- 익명 방문자와 일반 회원은 비활성 섹션의 공개 API 데이터나 새 파일 URL을 받을 수 없다.
- 편집자와 관리자는 `/manage`에서 비활성 섹션의 콘텐츠를 계속 조회·작성·수정할 수 있다.
- 기존 데이터와 설정은 migration 직후 모두 활성 상태로 유지된다.
- 설정 또는 상태 확인 장애가 비활성 콘텐츠를 공개하는 방향으로 실패하지 않는다.
